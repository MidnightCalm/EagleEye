# Eagle Eye — native shell

The web app, unchanged, inside an ARKit session.

Everything the PWA fought for — a fused lens, a flip-tested sensor bias, horizon
locks, panel ties, epochs — exists because a browser cannot tell you where the
camera is or what lens it has. ARKit tells you both, thirty times a second. This
shell is the smallest thing that hands those two facts to the app already
written.

```
native/            (inside the app repo)
├── project.yml              the whole Xcode project, in twenty readable lines
├── sync-web.sh              copies the repo root into www/ (one source of truth)
├── Sources/
│   ├── AppDelegate.swift
│   └── SurveyViewController.swift   ARSession + WKWebView + the bridge
└── www/                     generated by sync-web.sh — never edited
```

The other half of the bridge is `../eagle-eye/native.js`, which ships in the web
app too and is inert in a browser.

## What changes when it runs natively

| | PWA | native shell |
|---|---|---|
| Attitude | DeviceOrientation, per-device bias, shutter jerk | ARKit visual-inertial, drift-free |
| Lens | fused over panel shots, gated, re-fitted | factory intrinsics, exact, free |
| Position | none — shots tied by panel and landmarks | metric, continuous, every frame |
| Heading | compass, poor on a steel roof | true north via `.gravityAndHeading` |

The panel does not retire: it becomes the independent scale check on ARKit's
drift, which is the job it should always have had.

## Building it — the Mac side

Prerequisites: macOS with Xcode 15+, and:

```bash
brew install xcodegen
```

Then, from this folder:

```bash
./sync-web.sh
TEAM_ID=XXXXXXXXXX xcodegen        # your 10-character Apple team id
open EagleEye.xcodeproj
```

Select your iPhone, press Run. First launch asks for camera and motion.

`TEAM_ID` is the only project value that is yours. Set it once in your shell
profile and `xcodegen` picks it up every time:

```bash
echo 'export TEAM_ID=XXXXXXXXXX' >> ~/.zshrc
```

## Signing and TestFlight

Signing material — certificates, provisioning profiles, the App Store Connect
API key — is created in your Apple account and installed on the build machine.
None of it belongs in this repository and none of it should ever be pasted into
a chat window:

- **Local builds:** Xcode → Settings → Accounts → add your Apple ID → "Download
  Manual Profiles". Automatic signing then works with `TEAM_ID` alone.
- **TestFlight from CI:** create an App Store Connect API key (App Store Connect
  → Users and Access → Integrations → App Store Connect API), download the `.p8`
  **once**, and add it plus the key id and issuer id as GitHub repository
  secrets. `.github/workflows/ios.yml` reads them by name; it never sees them
  otherwise.

## Phases

1. **Shell** — the current app, installable, no ARKit dependence. Proves signing,
   TestFlight and the bundle. *This is what the scaffold builds today.*
2. **ARKit inputs** — `native.js` is already wired for it: pose into `ui.sensors`,
   factory intrinsics into `fovByFrame`. Every existing screen gets better
   without being rewritten.
3. **Walk-capture** — `EENative.captureFrame()` returns a JPEG and the pose it
   was taken at, so a shot is born registered; keyframes bank automatically on
   travel or turn. Tapping moves off the roof and into review.
4. **Plane proposals** — ARKit segments horizontal planes continuously, and a
   rooftop is horizontal planes all the way down: RTU tops arrive as rectangles
   at known heights. Confirm, name, export. Plus DXF for CAD, and the LiDAR mesh
   as a bonus where sunlight allows.

## What is verified, and what is not

The coordinate conversions are proven in `../eagle-eye/tools/test-geo.html`:
ARKit's frames round-trip against this app's attitudes exactly, the physical
sanity case (upright portrait, rear camera north) is checked independently of
the algebra, and factory intrinsics map to the stored field of view. That is
real, and it was verified without a Mac.

The Swift has never been compiled — it was written on a Windows machine. Expect
the first build to want small corrections, and expect the interface-orientation
handling to be the thing that needs a device to confirm.
